# גלריית שמחת התורה

אתר גלריה פרטי המבוסס על GitHub Pages ו־Cloudflare בלבד. Firebase אינו נדרש להפעלת האתר.

## רכיבי המערכת

- `index.html` — מבנה ה־HTML בלבד, וקישורים לגיליון הסגנון ולמודולים.
- `admin.html` — לוח הניהול כדשבורד: ניווט קבוע בצד ומסך אחד פעיל במרכז.
- `styles.css` — מערכת העיצוב "ארכיון האורורה" של האתר ושל הלוח, בנויה על אסימוני CSS.
- `app.js` — נקודת הכניסה: אתחול, מצב משותף, עזרים וטעינה עצלה של מודולים.
- `error-monitor.js` — ניטור שגיאות בצד הלקוח: מאזינים גלובליים ו־`window.reportClientError`.
- `popup-announcement.js` — הודעת הפופ-אפ למבקרים והפניה ליעדים שבאתר.
- `tailwind.generated.css` — פלט בנוי של Tailwind. **אין לערוך ידנית.**
- `gallery.js` — הצגת הגלריה, מדיה, ניווט ותיקיות.
- `gallery-feed.js` — שכבת הנתונים של דף הגלריה: תמונות לפי תיקייה בעמודים, מונים מהשרת והחדשות ביותר (ראה "שכבת הנתונים").
- `drive-sync.js` — חיבור וסנכרון Google Drive, סריקה רקורסיבית ותיקיות. הסנכרון מוסיף בלבד: קבצים ותיקיות שנמחקו ב־Drive נשארים באתר.
- `admin.js` — לוגיקת הניהול: משתמשים, דרגות, הרשאות ואישור תוכן.
- `admin-ui.js` — שכבת הממשק של הלוח: רשימת המסכים, הניווט, החיפוש והכלים.
- `admin-errors.js` — מסך "שגיאות ותקלות" בלוח הניהול; נטען עצלה בפתיחת המסך.
- `face-search.js` — חיפוש הפנים: הפקת טביעה מתמונת החיפוש והשוואה בענן.
- `face-index.js` — הכנת חיפוש הפנים: אינדוקס חד־פעמי של הגלריה ואינדוקס אוטומטי לתמונות חדשות.
- `media-variants.js` — תצוגות מקדימות למדיה: בחירת המקור להצגה ובחירת הפריטים שעדיין חסרות להם תצוגות (בלי DOM, נבדק ב־Node).
- `media-variants-generate.js` — יצירת התצוגות בדפדפן: הקטנה ב־Canvas, קידוד WebP ופריים מסרטון; נטען עצלה בהעלאה.
- `media-variants-admin.js` — מסך "תצוגות מקדימות" בלוח הניהול: ריצת ההשלמה למדיה הקיימת.
- `upload-queue.js` — תור ההעלאה: מקביליות, ביטול, ניסיון חוזר עם השהיה גדלה וסיכום (בלי DOM).
- `upload-resumable.js` — העלאה בחלקים שממשיכה אחרי ניתוק או רענון (R2 multipart, מצב ב־IndexedDB).
- `upload-compress.js` — הקטנת תמונה ענקית לפני העלאה, ושמירת תאריך הצילום מ־EXIF.
- `stream-player.js` — ניגון HLS מ־Cloudflare Stream בתצוגה המלאה, כשהוא מוגדר (רשות).
- `video-hover-preview.js` — תצוגה מקדימה מושתקת של סרטון בריחוף או במיקוד על הכרטיס.
- `capture-date.js` — קריאת תאריך הצילום מהקובץ (EXIF של JPEG/HEIC/WebP, `mvhd` של MP4/MOV) ועזרי המיון לפי `takenAt` (בלי DOM, נבדק ב־Node).
- `hebrew-date.js` — הלוח העברי, מקומית ובלי רשת: המרה מתאריך לועזי ועיצוב באותיות ("י״ז בתשרי תשפ״ז").
- `capture-dates-admin.js` — מסך "תאריכי צילום" בלוח הניהול: ריצת ההשלמה של `takenAt` למדיה הקיימת.
- `cloudflare-client.js` — התחברות Google ישירה ושכבת הנתונים של D1.
- `api-environment.js` — לאיזה Worker האתר פונה: הייצור, או סביבת הניסוי ב־`*.pages.dev` וב־`localhost` (ראה "סביבת ניסוי").
- `cloudflare-worker.js` — API מאובטח, אימות Google, D1, R2, Drive, דוא״ל, חיפוש AI וחיפוש פנים.
- `cloudflare-d1-schema.sql` — מבנה מסד הנתונים.
- `sw.js` ו־`manifest.webmanifest` — התקנה כאפליקציה ומטמון מגורסן.

מנוע זיהוי הפנים אינו נטען בפתיחת האתר; הספרייה והמודלים יורדים רק
בפתיחת כלי חיפוש הפנים, פעם אחת לכל כניסה.

## חיפוש פנים בענן

### ניהול ואיחוד פרצופים

בלוח הניהול, פתח **פרצופים ואינדוקס**. בראש המסך מוצגות תצוגות של כל
הפרצופים שאונדקסו, ב־24 פרצופים לעמוד. אפשר לבחור פרצופים מעמודים שונים
וללחוץ **זה אותו אדם — איחוד**. אם הם כבר משויכים לקבוצות, הקבוצות מתאחדות.
לחיצה על מזהה קבוצה מציגה את חבריה; **הפרד מהאדם** מסיר פרצוף יחיד מהקבוצה.

האיחוד נשמר בענן ומשמש את החיפוש: התאמה לאחת מההופעות של אדם מחזירה גם
את התמונות המקושרות ידנית. אין שינוי בסף הזיהוי האוטומטי. תוצאות מקושרות
מסומנות ב־API כ־`source: manual` ללא אחוז התאמה ביומטרי מומצא.
מנהל או מנהל־על בלבד יכול לגשת ל־`GET/POST /face/people`.

התצוגות נחתכות מקומית מהתמונות באמצעות אותו מנוע זיהוי, רק עבור העמוד
הנוכחי ובמקביליות מוגבלת. הטעינה הראשונה עשויה להתארך; כשל בתצוגה אינו
מאפשר לבחור פרצוף שלא הוצג. טביעות הפנים השמורות אינן מוחזרות לדפדפן.
טבלת `face_people` נוצרת אוטומטית בפריסת ה־Worker. איפוס האינדוקס מוחק גם
את השיוכים הידניים; אינדוקס ששינה טביעה אינו מחיל עליה את השיוך הישן.

כל תמונה מעובדת פעם אחת בלבד, וטביעות הפנים שלה (וקטור של 128 מספרים לכל
פרצוף) נשמרות ב־D1. חיפוש רגיל אינו מוריד ואינו סורק מחדש את תמונות הגלריה:
הדפדפן מפיק טביעה מתמונת החיפוש בלבד, שולח אותה ל־Worker, וה־Worker מחזיר רק
מזהי תמונות עם מרחק ואחוז התאמה. תמונת החיפוש עצמה אינה נשמרת, ו־descriptors
אינם מוחזרים ללקוח ואינם נכתבים ליומן.

ערכי הסף נשמרו כפי שהיו: התאמה רגילה `0.62`, התאמה חזקה `0.48`.

### הכנה חד־פעמית של התמונות הקיימות

1. היכנס כמנהל, פתח את לוח הניהול ובחר **הכן חיפוש פנים בענן**.
2. לחץ **התחל או המשך אינדוקס**. התמונות מעובדות בקבוצות קטנות, והמסך מציג
   כמה הושלמו, כמה נותרו וכמה נכשלו.
3. אפשר לעצור בכל רגע. ההמשך — גם אחרי רענון או סגירת הדפדפן — מתחיל מהמקום
   שנעצר, משום שמצב האינדוקס נשמר ב־D1 ולא בדפדפן.
4. תמונה שכבר עובדה באותה גרסת מודל נידלגת, ותמונה שלא נמצאו בה פנים מסומנת
   כמעובדת כדי שלא תיסרק שוב. כישלון בתמונה אחת אינו עוצר את התהליך.

תמונה חדשה שמועלית או מאושרת נכנסת אוטומטית לאינדוקס ברקע; כישלון בזיהוי
הפנים אינו מעכב ואינו מכשיל את ההעלאה, והתמונה תיאסף בריצת האינדוקס הבאה.

### החלפת גרסת מודל

`FACE_MODEL_VERSION` מוגדר גם ב־`cloudflare-worker.js` וגם ב־`face-search.js`
וחייב להיות זהה בשניהם. שינוי הערך מחזיר את כל התמונות לתור האינדוקס באופן
אוטומטי, והחיפוש משתמש רק בטביעות של הגרסה הנוכחית. כפתור **איפוס ואינדוקס
מחדש** (מנהל־על) מוחק את כל הטביעות השמורות לפני סריקה נקייה.

### נקודות הקצה

| נתיב | הרשאה | תפקיד |
|---|---|---|
| `POST /face/search` | משתמש מחובר ומאושר | השוואת טביעה מול הגלריה; מחזיר `imageId`, `distance`, `confidence`, `strength` |
| `POST /face/index` | מנהל או תהליך אינדוקס | שמירה ועדכון של טביעות לתמונה (כמה פרצופים לתמונה) |
| `POST /face/index/pending` | מנהל או תהליך אינדוקס | אילו תמונות עדיין ממתינות לאינדוקס |
| `GET /face/index/summary` | משתמש מחובר ומאושר | מוני התקדמות בלבד |
| `POST /face/index/reset` | מנהל־על | מחיקת טביעות לפני אינדוקס מחדש |

כל נקודות הקצה מוגבלות בקצב, מספר התוצאות בחיפוש מוגבל, וכל טביעה נבדקת
לפני שמירה: בדיוק 128 מספרים סופיים בטווח סביר. מחיקת תמונה — ברשומה או
בקובץ שב־R2 — מוחקת גם את כל טביעות הפנים שלה.

## תצוגות מקדימות למדיה

הגלריה אינה מגישה עוד את קובץ המקור לכל כרטיס. לכל פריט מדיה נשמרות לצד
המקור גרסאות מוקטנות — "תצוגות" — שנוצרות **בדפדפן** (Canvas), בלי שירות
תמונות בתשלום:

| תצוגה | למה | צלע ארוכה | היכן מוצגת |
|---|---|---|---|
| `thumb` | תמונה וסרטון | 480px | כרטיס הגלריה, פסיפס הכניסה, רקע התצוגה המלאה, פוסטר הכרטיס של סרטון |
| `medium` | תמונה | 1280px | התצוגה המלאה, יחד עם `thumb` ב־`srcset` — טלפון מקבל את הקטנה, מסך גדול את הבינונית |
| `poster` | סרטון | 1280px | הפוסטר בתצוגה המלאה, במקום ריבוע שחור |

הקידוד הוא WebP (איכות 0.8 ל־`thumb`, 0.85 ל־`medium` ול־`poster`); דפדפן
שאינו יודע לקודד WebP (Safari ישן) מקודד JPEG, וסוג הקובץ נרשם ברשומה.

**AVIF.** דפדפן שיודע לקודד AVIF ב־Canvas שולח לכל תצוגה גם עותק AVIF —
רק אם הוא קטן מה־WebP/JPEG. העותק הוא תמיד תוספת: הגלריה מציעה אותו
ב־`<picture>` עם `<source type="image/avif">`, ודפדפן שאינו מפענח AVIF מקבל
את ה־WebP/JPEG כרגיל. נכון להיום רוב הדפדפנים מפענחים AVIF אך אינם מקודדים
אותו ב־Canvas (הם מחזירים PNG, והבדיקה `canEncodeAvif` מזהה זאת), ולכן ברוב
ההעלאות יישמר WebP בלבד; התשתית — ה־Worker, הרשומה והתצוגה — מוכנה לרגע
שהדפדפן יתמוך.

**`srcset` ו־`sizes`.** כרטיס של תמונה עם `thumb` ו־`medium` מקבל את שתיהן
ב־`srcset` עם `sizes` לפי רוחב העמודה (`CARD_IMAGE_SIZES` ב־`media-variants.js`):
טלפון ומסך רגיל טוענים את הקטנה, מסך רחב בצפיפות כפולה את הבינונית. התצוגה
המלאה מקבלת את אותו `srcset` עם `sizes="100vw"`.
הכיוון שב־EXIF נשמר (`createImageBitmap` עם `imageOrientation: 'from-image'`),
ואף תצוגה אינה גדולה מהמקור: קובץ קטן מהגבול נשאר בממדיו ורק מקודד מחדש.
לסרטון נשלף פריים אחד בסביבות השנייה הראשונה (או הפריים הראשון שניתן
לפענח, כשהמשך אינו ידוע).

**המקור נשמר תמיד.** ההורדה מהתצוגה המלאה מביאה אותו, אינדוקס הפנים ממשיך
לעבוד מולו, ותצוגה שאינה נטענת (למשל קובץ שנמחק) נופלת אליו לפני שמוצג
ממלא מקום. ה־Service Worker אינו נוגע בתצוגות: מדיה חוצת־מקור אינה נשמרת
במטמון שלו, והתצוגות נשמרות במטמון הדפדפן הרגיל.

### היכן זה נשמר

- ב־R2: `variants/<imageId>/<thumb|medium|poster>.<webp|jpg>` (ועותק
  `.avif` כשנשלח), עם
  `Content-Type` מתאים ו־`Cache-Control: public, max-age=31536000, immutable`
  לפריט מאושר. תצוגה של פריט ממתין מוגשת רק למי שהעלה אותו ולמנהלים, ואחרי
  האישור (`POST /approve`) היא מסומנת כמאושרת יחד עם המקור.
- ברשומה (`images` וגם `pendingImages`): `variants: { thumb: { key, url, width,
  height, type, avif?: { key, url, type } }, medium: {…}, poster: {…} }`
  ו־`variantsVersion: 1`. הכתובות נבנות בדיוק כמו כתובת המקור (`/media/<key>`
  באותו מקור של ה־API). תצוגה חדשה שנשלחה בלי AVIF מוחקת את עותק ה־AVIF
  הישן שלה, כדי שלא יוצג קובץ שאינו תואם.
- ב־D1, בטבלה `media_variant_files`: שורה לכל קובץ תצוגה (מפתח, פורמט, ממדים,
  גודל). הרשומה היא עדיין המקור לכתובות; הטבלה משמשת רק את שורת הנפח במסך
  הניהול, ונמחקת יחד עם הקבצים. כשל בכתיבה אליה אינו מכשיל שמירה.
- מחיקת הפריט — הרשומה או קובץ המקור ב־R2 — מוחקת גם את התצוגות שלו, כמו
  את טביעות הפנים. פריט ששוחזר מסל המחזור חוזר בלי `variants` ונאסף שוב
  בריצת ההשלמה הבאה. רשומה שנכתבת מעותק ישן בלי `variants` אינה מוחקת
  אותן: ה־Worker משאיר את מה שכבר נרשם.

### איך הן נוצרות

1. **בהעלאה.** `uploadMediaToR2` שב־`app.js` — נקודת המעבר של כל העלאת גלריה:
   משתמש, מנהל, סנכרון Drive (שמוריד את הקובץ לדפדפן) ופוסטר הסרטון — טוענת
   עצלה את `media-variants-generate.js`, מייצרת את התצוגות ושולחת אותן באותו
   טופס עם המקור כחלקים `variant_thumb` / `variant_medium` / `variant_poster`
   ושדה `variantsMeta` עם הממדים. ה־Worker מחזיר `variants` בתשובת ההעלאה,
   והלקוח מעתיק אותן לרשומה שהוא כותב. **כישלון ביצירה לעולם אינו עוצר
   העלאה**: הקובץ עולה בלעדיהן ונרשם ביומן, והריצה הבאה משלימה.
2. **למדיה הקיימת.** בלוח הניהול, מסך **תצוגות מקדימות**: המונה מציג כמה
   פריטים חסרים תצוגות (הרשומות נקראות מה־API, לא מהמצב המקומי), ולחיצה על
   **התחל או המשך** מעבדת אותם — עד שלושה במקביל — מורידה את המקור לדפדפן
   של המנהל, מייצרת את התצוגות ושולחת ל־`POST /media/variants`. סרטון מאושר
   אינו יורד כולו: `<video>` מושך רק את הטווח שנחוץ לפריים. אפשר לעצור בכל
   רגע; ההמשך — גם אחרי רענון — מדלג מאליו על מה שכבר נשמר, כי הריצה בוחרת
   רק פריטים שחסרות להם התצוגות הנדרשות לסוגם. כישלון בפריט אחד מופיע
   ברשימת הכשלונות ואינו עוצר את השאר. פריט שאינו מאוחסן ב־R2 של הגלריה
   (קישור חיצוני ישן) נספר בנפרד ואינו מעובד — אין ממנו CORS.

### נקודות הקצה והמגבלות

| נתיב | הרשאה | תפקיד |
|---|---|---|
| `POST /upload` | כמו קודם | מקבל גם את החלקים `variant_*` ו־`variantsMeta`; מחזיר `variants` ו־`variantsVersion` |
| `POST /media/variants` | מנהל, או מי שהעלה את הפריט כל עוד הרשומה הממתינה שלו פתוחה | multipart עם `imageId` ואותם חלקים; מעדכן את הרשומה ב־`images` וב־`pendingImages` |
| `GET /media/variants/<imageId>/<שם>.<webp\|jpg\|avif>` | ציבורי לפריט מאושר; הבעלים ומנהלים לפריט ממתין | הגשת התצוגה עם מטמון ארוך |
| `GET /media/variants/stats` | מנהל | `{ files, bytes, images, byFormat }` מטבלת `media_variant_files`, לשורת הנפח במסך "תצוגות מקדימות" |

כל תצוגה חייבת להיות `image/webp` או `image/jpeg` ועד 2MB, ועותק ה־AVIF שלה
(`variant_<שם>_avif`) — `image/avif` ועד 2MB, ורק יחד עם התצוגה הרגילה באותה
בקשה (אחרת `avif_without_variant`); חלק פסול מכשיל את
הבקשה כולה לפני שנשמר דבר. `POST /media/variants` מוגבל ל־1,500 בקשות לכל
משתמש בחמש דקות, והריצה ממתינה ומנסה שוב כשהמכסה מתמלאת. חלק מהתצוגות
(למשל `medium` לסרטון) אינו חובה; ריצת ההשלמה דורשת `thumb` ו־`medium`
לתמונה ו־`poster` לסרטון. הקובץ המקורי אינו נבדק מחדש ואינו משתנה.

### מיגרציה ופריסה

- **D1:** הטבלה `media_variant_files` והאינדקס שלה נוספו ל־`cloudflare-d1-schema.sql`.
  ה־Worker יוצר אותם בעצמו בבקשה הראשונה אחרי הפריסה (`CREATE TABLE IF NOT
  EXISTS`, גרסת הסכימה עולה ל־5), ואין צורך בצעד ידני. מי שמעדיף ליצור אותם
  מראש מריץ שוב את תוכן `cloudflare-d1-schema.sql` ב־**Console** של המסד —
  בייצור ובסביבת הניסוי; כל ההוראות בו אידמפוטנטיות. לא נוסף עמוד לרשומות
  קיימות: `variants` נשמר בתוך `data_json`.
  גרסת הסכימה (המפתח `gallery` ב־`gallery_schema_meta`) רק עולה — Worker ישן
  שנפרס שוב אינו מוריד אותה — ואינה נוגעת בגרסאות הנתונים של שכבת הנתונים
  (`data_version:<אוסף>` באותה טבלה). צירוף תצוגות לרשומה מקדם את גרסת
  הנתונים של `images`/`pendingImages`, כך שה־ETag ומטמון הקצה מתיישנים מיד.
  `cloudflare-worker-schema-migration.test.mjs` מריץ את המעבר על מסד בגרסה 4.
- **סדר הפריסה:** קודם ה־Worker, אחר כך האתר. אתר חדש מול Worker ישן עדיין
  עובד — ההעלאה נשמרת בלי תצוגות (ה־Worker הישן מתעלם מהחלקים הנוספים),
  ומסך "תצוגות מקדימות" מודיע שנקודת הקצה אינה זמינה.
- **אחרי הפריסה:** בלוח הניהול, מסך **תצוגות מקדימות** → **התחל או המשך**, כדי
  להשלים תצוגות למדיה שהועלתה קודם. אפשר לעצור ולהמשיך; פריטים שכבר הושלמו
  אינם מעובדים שוב. התצוגות של מדיה קיימת נוצרות בדפדפן של המנהל, ולכן כדאי
  להריץ ממחשב ולא מטלפון.
- **לחזור אחורה:** האתר ממשיך לעבוד גם בלי התצוגות — רשומה בלי `variants`
  מוצגת מהמקור, כמו קודם. הקבצים שב־`variants/` אפשר למחוק מ־R2 בלי לפגוע
  במקור.

## העלאות: תור, הקטנה לפני שליחה, והעלאה בחלקים שממשיכה אחרי ניתוק

### תור ההעלאה

בחלון ההעלאה אפשר לבחור הרבה קבצים בבת אחת. כל קובץ מקבל שורה עם סרגל
התקדמות, מצב (ממתין, מעבד, מעלה, ממתין לניסיון חוזר, הושלם, נכשל, בוטל)
וכפתור ביטול משלו; מעל התור מוצגים סרגל כולל ושורת סיכום ("הושלמו 3 מתוך 5 ·
נכשלו 1"). שני קבצים עולים במקביל. כשל זמני — רשת, זמן קצוב, עומס (429) או
שגיאת שרת (5xx) — מנוסה שוב מאליו אחרי השהיה גדלה (1, 2, 4 שניות, עם רעד
קטן), עד ארבעה ניסיונות; כשל קבוע (סוג קובץ, גודל, הרשאה) מסומן מיד. אחרי
שהתור סיים, **נסה שוב קבצים שנכשלו** מחזיר לתור רק את מה שנכשל. הסיכום
והמצבים מוכרזים בקוראי מסך (`aria-live`), האחוזים מוצגים לעין בלבד כדי לא
להציף בהכרזות, וכל הצבעים מאסימוני `styles.css`.

הלוגיקה ב־`upload-queue.js` (ללא DOM, נבדקת ב־Node), הממשק ב־`gallery.js`.
`upload-queue.js`, `upload-resumable.js` ו־`upload-compress.js` נטענים עצלה,
רק כשמישהו באמת מעלה, ולכן אינם ב־`APP_SHELL` של ה־Service Worker.

### הקטנה לפני ההעלאה

עד כה כל תמונה הוקטנה ל־800 פיקסלים באיכות 0.6 ונשמרה כך — זה היה ה"מקור"
שבגלריה. עכשיו (`upload-compress.js`): תמונה שהצלע הארוכה שלה מעל **3840**
פיקסלים, או שנפחה מעל 3MB, מוקטנת ל־3840 ומקודדת מחדש באיכות **0.85** — JPEG
לתמונות JPEG/HEIC, WebP ל־PNG/WebP (שקיפות). תמונה קטנה מזה עולה כמות שהיא,
וגם קידוד שלא הקטין את הקובץ מוותר לטובת המקור. GIF אינו מקודד מחדש.

- **כיוון:** הפענוח מיישם את ה־EXIF Orientation, והקובץ החדש כבר עומד נכון.
- **תאריך הצילום:** קידוד ב־Canvas מוחק את ה־EXIF, ולכן הוא נקרא מהקובץ
  המקורי לפני ההקטנה: שדות `takenAt`/`takenDate`/`takenAtOffset`/`takenAtSource`
  (ראו "תאריך הצילום והתאריך העברי") נקבעים מהמקור, ובנוסף `capturedAt` נשלח
  ל־Worker ונרשם במטא־דאטה של הקובץ ב־R2.
- **"שליחת הקבצים המקוריים"**: מתג בחלון ההעלאה שמוצג למנהלים בלבד. כשהוא
  מסומן הקובץ עולה בלי שינוי (חוץ מסוג שה־Worker אינו מקבל, כמו HEIC, שתמיד
  מקודד ל־JPEG).

### העלאה בחלקים שאפשר להמשיך (R2 multipart)

קובץ גדול מ־8MiB (בעיקר סרטון מהטלפון) עולה בחלקים של 8MiB דרך
`upload-resumable.js`; קטן מזה ממשיך לעלות בבקשה אחת (`POST /upload`) כמו
קודם. מצב ההעלאה נשמר בשני מקומות:

- **ב־D1** (`upload_sessions`, `upload_session_parts`): אילו חלקים התקבלו. זה
  המקור הקובע.
- **בדפדפן (IndexedDB, `simchas-gallery-uploads`)**: לאיזו העלאה שייך הקובץ —
  לפי טביעה (שם, גודל, תאריך שינוי ו־SHA-256 של תחילת הקובץ וסופו, לכל משתמש
  בנפרד) — ואיזה מזהה מדיה הוקצה לו.

ניתוק באמצע: הניסיון החוזר האוטומטי שואל את ה־Worker מה התקבל וממשיך מהחלק
הבא. **רענון או סגירת הדף:** בפתיחת חלון ההעלאה מופיעה תזכורת להעלאות שלא
הושלמו; בחירה מחודשת של אותו קובץ מסמנת אותו "ימשיך מהנקודה שנעצר", והוא
ממשיך מאותו חלק, עם אותו מזהה מדיה. ביטול קובץ מבטל גם את ההעלאה ב־R2.
התצוגות המקדימות נוצרות רק לקראת ההשלמה ונשלחות איתה. סרטון שעולה בחלקים
יכול להגיע עד **1GB** (במקום 100MB בבקשה אחת), ותמונה עד 50MB.

| נתיב | הרשאה | תפקיד |
|---|---|---|
| `POST /upload/multipart/create` | כמו `/upload` (משתמש מאושר; צופה מעלה ל־`pending/`) | פותח העלאה: `{ imageId, title, fileName, mimeType, size, capturedAt }` → `{ uploadId, key, partSize, totalParts }` |
| `PUT /upload/multipart/part?uploadId=&partNumber=` | מי שפתח את ההעלאה | גוף: בייטים של החלק. כל חלק חייב להיות בדיוק 8MiB, מלבד האחרון |
| `GET /upload/multipart/status?uploadId=` | מי שפתח את ההעלאה | החלקים שהתקבלו — כדי להמשיך מהם |
| `POST /upload/multipart/complete` | מי שפתח את ההעלאה | טופס: `uploadId` ו־`variant_*` כמו ב־`/upload`. מחזיר בדיוק את צורת התשובה של `/upload`; השלמה חוזרת מחזירה את אותה תשובה |
| `POST /upload/multipart/abort` | מי שפתח את ההעלאה | מבטל ב־R2 ומוחק את המצב |

פתיחת העלאה נספרת במכסת ההעלאות הרגילה (60 בעשר דקות); החלקים — במכסה נפרדת
של 3,000 בעשר דקות. העלאה שלא נגעו בה שישה ימים מנוקה כשאותו משתמש פותח
העלאה חדשה (R2 מבטל בעצמו העלאה פתוחה אחרי שבוע).

## Cloudflare Stream (רשות): ניגון HLS לסרטונים

כברירת מחדל סרטונים מנוגנים מהקובץ שב־R2, בדיוק כמו קודם. כשב־Worker מוגדרים
שני הסודות `STREAM_ACCOUNT_ID` ו־`STREAM_API_TOKEN`, כל סרטון **מאושר** נשלח
בנוסף ל־Cloudflare Stream ("העתקה מכתובת" — Stream מושך את הקובץ מכתובת המדיה
הציבורית ב־R2, בלי העלאה נוספת מהטלפון). סרטון ממתין נשלח רק ברגע האישור, כדי
שעותק שלו לא יהיה ציבורי לפני כן. הרשומה מקבלת שדה `stream: { uid, hls, iframe }`,
והתצוגה המלאה מנגנת אז ב־HLS באותו נגן של האתר: Safari בעצמו, ושאר הדפדפנים
דרך hls.js שנטען מ־cdnjs רק כשבאמת צריך (`stream-player.js`). כל תקלה — סרטון
שעדיין בעיבוד ב־Stream, ספרייה שלא נטענה, שגיאת רשת — נופלת לקובץ שב־R2. כשל
מול Stream לעולם אינו מכשיל העלאה או אישור, ומחיקת הסרטון מהגלריה מוחקת גם את
העותק ב־Stream (טבלת `stream_videos`). `/health` מדווח `streamEnabled`.

**הפעלה (בעל המאגר, פעם אחת):**

1. בדשבורד של Cloudflare: **Stream** → להפעיל את השירות (בתשלום לפי דקות
   שמורות ונצפות).
2. **My Profile → API Tokens → Create Token** → הרשאה **Account → Stream → Edit**
   לחשבון הזה בלבד. להעתיק את האסימון.
3. **Workers & Pages → simchas-gallery-api → Settings → Variables and Secrets**:
   להוסיף `STREAM_ACCOUNT_ID` (מזהה החשבון, מופיע בצד ימין של דף הבית בדשבורד)
   ו־`STREAM_API_TOKEN` (Secret) — ולפרוס. אותו דבר ב־Worker של הניסוי, אם רוצים
   לנסות שם קודם.
4. לבדוק: `/health` מחזיר `"streamEnabled": true`. סרטונים שיועלו או יאושרו
   מעכשיו יקבלו HLS; סרטונים ישנים ממשיכים להתנגן מ־R2.

**כיבוי:** למחוק את שני הסודות. רשומות שכבר נושאות `stream` ממשיכות לנסות HLS
ונופלות ל־R2 אם Stream אינו זמין; העותקים ב־Stream נמחקים ידנית מהדשבורד.

## תצוגה מקדימה של סרטון בריחוף

כרטיס סרטון בגלריה מציג את הפוסטר מהתצוגות המקדימות, וה־`<video>` שבו נשאר
`preload="none"` — שום בייט של הסרטון אינו יורד עד שמתעניינים בו. ריחוף בעכבר,
או מיקוד במקלדת, מנגן את הסרטון מושתק ובתוך הכרטיס כארבע שניות (פס דק בתחתית
מסמן את הזמן), ויציאה עוצרת וחוזרת לפוסטר. פתיחת התצוגה המלאה עוצרת את
התצוגה המקדימה. כבוי למי שביקש פחות תנועה (`prefers-reduced-motion`) ובמכשיר
מגע בלבד. מאזין אחד לכל הרשת (`video-hover-preview.js`), ולכן גם כרטיסים
שנוספים בגלילה עובדים.

### מיגרציה ופריסה של השינויים האלה

- **D1:** גרסת הסכימה עולה ל־**7**: `upload_sessions` (עם האינדקס
  `idx_upload_sessions_owner`), `upload_session_parts` ו־`stream_videos`. ה־Worker
  יוצר אותן בעצמו בבקשה הראשונה אחרי הפריסה, כמו בגרסאות הקודמות; אין צעד ידני.
  `cloudflare-d1-schema.sql` עודכן למי שמעדיף להריץ אותו ב־Console.
- **R2:** אין צורך בהגדרה — העלאה בחלקים היא חלק מ־R2 binding הקיים.
- **סדר הפריסה:** קודם ה־Worker, אחר כך האתר. אתר חדש מול Worker ישן: קבצים עד
  8MiB עולים כרגיל; קובץ גדול יותר ייכשל (הנתיב החדש אינו קיים) — לכן ה־Worker קודם.
- **סודות:** אין חובה. `STREAM_ACCOUNT_ID` ו־`STREAM_API_TOKEN` הם רשות (ראו למעלה).

## תאריך הצילום והתאריך העברי

כל פריט מוצג וממוין לפי **יום הצילום** שלו, ולא לפי יום ההעלאה, ובתאריך עברי.

### מה נשמר ברשומה

| שדה | משמעות |
|---|---|
| `takenAt` | רגע הצילום (ms). חסר — הפריט ממוין ומוצג לפי `createdAt` (זמן ההעלאה), כמו קודם |
| `takenDate` | `YYYY-MM-DD` כפי שהשעון של המצלמה הראה — ממנו נגזר התאריך העברי |
| `takenAtOffset` | `+03:00` כשהקובץ מציין אזור זמן (`OffsetTimeOriginal` וכו׳) |
| `takenAtSource` | `exif` / `video` / `drive`, או `none` — "נבדק ולא נמצא תאריך" |

### מאיפה מגיע התאריך

- **העלאה מהאתר** (`processFilesWithFolders` ב־`gallery.js`): התאריך נקרא מהקובץ **המקורי** לפני
  הדחיסה ב־Canvas (שמוחקת את ה־EXIF). `capture-date.js` קורא רק את הבתים הנחוצים:
  APP1 של JPEG, מקטע `EXIF` של WebP, פריט ה־Exif של HEIC (דרך `iinf`/`iloc`), ו־`creation_time`
  של `moov/mvhd` בסרטון (גם כש־`moov` בסוף הקובץ). מה־EXIF נלקח `DateTimeOriginal`, ואחריו
  `CreateDate`. בלי אזור זמן השעה מתפרשת כשעון המקומי של המעלה. כישלון בקריאה לעולם אינו עוצר העלאה.
- **סנכרון Drive**: הרשימה מבקשת גם `imageMediaMetadata(time)`; הקובץ שירד נקרא בכל זאת
  (`prepareMediaRecordForCloud`), ו־EXIF עם אזור זמן גובר על התאריך של Drive. ל־`videoMediaMetadata`
  אין זמן צילום ב־API, ולכן סרטון נקרא מהבתים. קובץ שלא השתנה ב־Drive ואין לרשומה שלו תאריך
  מקבל אותו מהמטא־דאטה, בלי הורדה.
- **מדיה קיימת** — מסך **תאריכי צילום** בלוח הניהול (ראו להלן).

### מיון, תצוגה וסינון

- "החדש ביותר" / "הישן ביותר" ממיינים לפי `takenAt` (ובלעדיו `createdAt`), ובשוויון לפי זמן
  ההעלאה ואז המזהה. ההזנה מהענן ממשיכה להגיע בעמודים לפי `createdAt` (החדש שנוסף ראשון);
  המיון לפי הצילום נעשה בדפדפן על מה שנטען. ה־Worker תומך גם ב־`?orderBy=takenAt` עם אינדקס.
- הכרטיס מציג את התאריך העברי (`.gallery-hebrew-date`, והלועזי בתיאור), התצוגה המלאה מציגה
  "צולם בי״ז בתשרי תשפ״ז (28.09.2026)" — או "הועלה ב…" כשאין תאריך צילום — וכותרת האירוע מציגה את
  תאריך האירוע שהוזן בעברית, ובלעדיו את טווח ימי הצילום. במיון לפי תאריך, הכרטיס הראשון של כל
  חודש עברי נושא תווית "תשרי תשפ״ז" (`.gallery-date-group`).
- בסרגל הכלים: `#galleryHebrewYearFilter` ו־`#galleryHebrewMonthFilter`. האפשרויות נגזרות מהפריטים
  שבתיקייה, ואדר א׳ / אדר ב׳ / אדר הם חודשים נפרדים. סינון פעיל בתיקייה שלא נטענה כולה מושך את
  שאר העמודים ברקע, כמו חיפוש.

### הלוח העברי

`hebrew-date.js` הוא מימוש אריתמטי של הלוח הקבוע (מולד תשרי והדחיות: מולד זקן, גטר״ד, בטו תקפ״ט,
לא אד״ו ראש), בלי רשת ובלי תלות ב־Intl. הבדיקות משוות אותו לכל יום בין 1900 ל־2100 מול
`Intl.DateTimeFormat('he-u-ca-hebrew')`, ולכל ראש שנה בין תר״ס לתתק״ס מול מימוש שני של הדחיות.
ICU (ש־Intl נשען עליו, נכון ל־Node 22) טועה ביום בין נובמבר 2045 לנובמבר 2046 — ראש השנה תתק״ז חל
ביום שני 1.10.2046 — ולכן החלון הזה מוחרג מההשוואה ומתועד בבדיקה.

**אין תיקון שקיעה.** תאריך הצילום משמש כתאריך קלנדרי בלבד: תמונה שצולמה בליל שבת אחרי השקיעה
מקבלת את התאריך העברי של יום שישי, אף שלפי ההלכה היום העברי כבר התחלף. אין כאן מיקום ושעות
שקיעה, ולכן הבחירה מכוונת.

### ה־Worker ו־D1

- כל כתיבה ל־`images` / `pendingImages` עוברת `normalizeCaptureFields`: `takenAt` חייב להיות מספר
  בין 1971 לעכשיו ועוד יומיים, אחרת כל שדות הצילום נמחקים; `takenDate` שאינו מתאים ל־`takenAt`
  (בטווח אזורי הזמן) נגזר מחדש; היסט או מקור פסולים נמחקים. כתיבה מעותק ישן בלי שדות הצילום
  משאירה את מה שנשמר (כמו `variants`).
- `GET /media/probe/<imageId>?offset=&length=` — מנהלים בלבד: עד 256KB מקובץ המקור שב־R2, עם
  `X-Media-Size`. `POST /media/taken-at` — מנהלים בלבד: `{ updates: [...] }` עד 50 בבקשה; מעדכן את
  הרשומה בשני האוספים ומקדם את גרסאות הנתונים (ETag ומטמון הקצה מתיישנים). `none` אינו מוחק תאריך קיים.
- **סכימה 6:** האינדקס `idx_gallery_documents_taken_at` (על הביטוי של `?orderBy=takenAt`). ה־Worker
  יוצר אותו בבקשה הראשונה אחרי הפריסה; אין צורך בצעד ידני, ואין עמודה חדשה — השדות בתוך `data_json`.

### השלמה למדיה קיימת (פעם אחת, אחרי הפריסה)

לוח הניהול → **תאריכי צילום** → **התחל או המשך**. הריצה בוחרת רק פריטים שעוד לא נבדקו, ולכל אחד:
קובץ מ־Drive כשהחיבור ל־Drive פעיל — `imageMediaMetadata.time`; אחרת — קריאת תחילת הקובץ מ־R2 דרך
`/media/probe` (סרטון שה־`moov` שלו בסוף נקרא בקפיצה, לא כולו). גם "לא נמצא" נרשם, ולכן אפשר לעצור
ולהמשיך. תמונות שהועלו מהאתר לפני התכונה נשמרו דחוסות ובלי EXIF, ולכן יישארו לפי יום ההעלאה;
תמונות מ־Drive וסרטונים נשמרו כמקור ויקבלו תאריך.

## מערכת העיצוב ושני מצבי התצוגה

העיצוב בנוי על שכבה אחת של אסימוני CSS. אין בקוד הרכיבים צבע קבוע: כל צבע
מגיע ממשתנה, וכל משתנה מוגדר פעמיים בלבד — במצב הכהה ובמצב הבהיר.

הדבר נכון גם ל־utilities של Tailwind. `tailwind.config.js` מפנה כל גוון אל
משתנה CSS (`--p-slate-400`, `--p-white` וכן הלאה), והסולם במצב הבהיר הוא
הסולם הכהה **בסדר הפוך**: 950 הופך ל־50, 400 ל־600 וכן הלאה. לכן `bg-white/5`
או `text-slate-400` שנכתבים בתוך מחרוזת ב־JS מקבלים ערך מתאים בשני המצבים
מאליהם, וכל צמד של "רקע כהה + טקסט בהיר" הופך לצמד "רקע בהיר + טקסט כהה"
בלי לאבד ניגודיות.

**אין להוסיף שכבת תיקונים למצב הבהיר.** הגרסה הקודמת החזיקה כ־180 כללי
`html[data-theme="light"] … !important` שדרסו רכיב־רכיב, וכל רכיב חדש נולד
שבור עד שנוסף לו תיקון. אם רכיב אינו נראה נכון במצב אחד — הצבע שלו נכתב
בקוד במקום להגיע מאסימון, וזה מה שיש לתקן.

צבעים שנשארים זהים בשני המצבים הם אלה שיושבים מעל מדיה: התצוגה המלאה
(`#lightboxModal`), מספור הכרטיס ורצועת "תצוגה מלאה" שעליו.

### שפת העיצוב: "ארכיון האורורה"

- **שני גופנים.** Assistant לטקסט רץ, ו־Frank Ruhl Libre (700/900) לכותרות
  ולמספרים הגדולים — `--font-display`. זה מה שנותן לאתר אופי של אלבום מודפס.
- **רקע חי ב־CSS בלבד.** `#bg-container` מכיל ארבעה כתמי אורורה (`.aurora-orb`),
  סבכה עדינה (`.bg-grid`) ושכבת גרעין (`.bg-grain`). הכתמים מונפשים
  ב־`transform` בלבד, נעצרים כשהמשתמש ביקש פחות תנועה, ובטלפון נשארים
  שניים מהם ובלי גרעין. הקנבס `#ambientCanvas` נשאר כבוי.
- **זהב כמבטא.** `--gold-foil` הוא הגרדיאנט של הכפתורים הראשיים, של סמל
  המותג ושל הכותרת הראשית; לכפתור ראשי יש הבזק אור בריחוף.
- **זכוכית במקומות ספורים.** `backdrop-filter` רק על הכותרת הצפה, סרגל
  הכלים, מדף התיקיות, פאנל הפרופיל, המגירה והחלונות — לא על כרטיסי הגלריה.
- **ספוט־לייט.** כרטיס גלריה ומחוון ניהול מקבלים `--mx`/`--my` ממאזין
  `pointermove` יחיד ב־`app.js` (עכבר בלבד), והזוהר עצמו הוא `::before`/`::after`.

מה שנוסף לאתר עם העיצוב הזה, בלי לגעת בנתונים:

| רכיב | היכן | מה הוא עושה |
|---|---|---|
| פסיפס הרגעים | `#heroMosaic`, `renderHeroMosaic` ב־`gallery.js` | עד חמש מהתמונות החדשות בפוסטר הכניסה; ריק — משטח דקורטיבי |
| מונים עולים | `window.animateCounter` | מספרי הפוסטר עולים בהדרגה אל הערך |
| צפיפות התצוגה | `.density-toggle`, `window.setGalleryDensity` | צפוף / רגיל / גדול, נשמר ב־`localStorage` |
| השתקפות בתצוגה המלאה | `#lightboxBackdrop` | התמונה הנוכחית (או פוסטר הסרטון) כרקע מטושטש |
| פס גלילה וחזרה למעלה | `.scroll-progress`, `#backToTop` | מאזין גלילה אחד, מסונכרן לפריים |
| קיצור `/` | `initArchiveExperience` | מקפיץ לחיפוש הגלריה, כמו בלוח הניהול |

| טעינה מוקדמת בתצוגה המלאה | `preloadLightboxNeighbours`, `loadDecodedImage` | השכנים נטענים מראש, והתמונה מתחלפת רק אחרי פענוח |

### רינדור הדרגתי של הגלריה

הגלריה אינה בונה את כל הכרטיסים בבת אחת. `renderImages` שומר את הרשימה
המסוננת והממוינת במלואה, בונה מיד את 48 הכרטיסים הראשונים, ומוסיף 48 נוספים
בכל פעם שהזקיף `#gallerySentinel` שבסוף הרשת מתקרב למסך (`IntersectionObserver`
עם שוליים של 900px, כך שהמנה הבאה מוכנה לפני שמגיעים אליה). אחרי כל מנה
הזקיף נצפה מחדש: אם הוא עדיין בטווח — מסך גבוה, תצוגה צפופה — המנה הבאה
מגיעה בלי גלילה נוספת. בדפדפן בלי `IntersectionObserver` הרשת נבנית במלואה.

מה נשאר בדיוק כפי שהיה: החיפוש, המיון, מצב „אין פריטים”, בחירה מרובה, סימוני
המועדפים והמספור. התצוגה המלאה עובדת על הרשימה המלאה ולא על מה שצויר, ולכן
„הבא” מהכרטיס ה־48 מגיע לפריט ה־49 גם כשאין לו עדיין כרטיס.

רינדור מחדש מבחין בין שני מקרים. שינוי תצוגה — תיקייה, חיפוש, מיון או סינון
זמני — מחזיר את הרשת למנה הראשונה. עדכון נתונים באותה תצוגה — סנאפשוט חדש,
לב שנלחץ, חזרה ללשונית — שומר את מספר הכרטיסים שכבר הוצגו, כדי שהדף לא
יתקצר מתחת לגלילה של המשתמש, ומחליף רק כרטיסים שהמרקאפ שלהם השתנה
(`syncGalleryCards`): רענון שלא שינה דבר אינו נוגע ב־DOM, ולב מחליף כרטיס אחד.

כרטיס שלא השתנה נשאר אותו אלמנט — רק המספר שלו נכתב מחדש — ולכן תמונה חדשה
בראש הרשימה אינה בונה את הרשת מחדש. לפני רינדור כזה נרשם הכרטיס הראשון שבראש
המסך, ואחריו הגלילה מתוקנת בהפרש שבו זז, כך שהמשתמש נשאר מול אותו כרטיס.
מעבר לתצוגה אחרת כשגוללים עמוק בתוך הרשת גולל לראשה.

**חיבור לעימוד בשרת (`gallery-feed.js`).** `state.images` מחזיק רק את העמודים
שכבר הורדו לתיקייה הפעילה (120 בכל עמוד). כשהזקיף מגיע לסוף מה שהורד ו־
`state.imagesHasMore` דלוק, `renderMoreImages` קורא ל־`window.loadMoreImages`
פעם אחת — אין בקשה שנייה כל עוד הראשונה פתוחה — ו„טוען עוד...”
(`#galleryLoadingStatus`, `role="status"`) מוצג עד שהעמוד מגיע; אז מצטרפת מיד
מנה ממנו. הכפתור „טען פריטים ישנים יותר” (`fetchOlderImages`) עובר באותו מסלול.
תשובה שלא הוסיפה דבר אינה חוזרת על עצמה מאליה. לפני כל מנה הזקיף בודק את
מיקומו בפועל, ונתונים שהגיעו וטרם צוירו נצבעים לפני כל פנייה לענן — כך טעינת
הדף אינה מושכת עמודים בלי שהמשתמש גלל.

### טעינה מוקדמת ופענוח בתצוגה המלאה

בפתיחת התצוגה המלאה ובכל מעבר נטענים מראש הפריט הבא והקודם: לתמונה בדיוק
המקור שהתצוגה תציג (`pickLightboxSource` — התצוגה הבינונית עם אותם `srcset`
ו־`sizes`, בתוך `<picture>` מנותק עם מקור AVIF כשיש), ולסרטון הפוסטר בלבד —
לעולם לא קובץ הווידאו. לכל היותר ארבע טעינות נשמרות בו־זמנית; הישנה נזנחת, ואם טרם הסתיימה
ההורדה שלה מבוטלת. במצב חיסכון בנתונים (`navigator.connection.saveData`) אין
טעינה מוקדמת כלל.

המעבר בין תמונות אינו מהבהב: התמונה הקודמת נשארת על המסך, מעומעמת מעט
(`.lightbox-stage.is-loading`), עד שהבאה הורדה ופוענחה (`img.decode()`, ובלעדיו
אירוע `load`), ורק אז מתחלפות יחד התמונה וההשתקפות שברקע. דפדוף מהיר מציג רק
את התמונה האחרונה שנבחרה, ואחרי שש שניות בלי פענוח התמונה מוצגת בכל מקרה.
הכותרת, הפרטים והמונה מתעדכנים מיד, עוד לפני הפענוח.

שדות הקלט פותחים ב־`body` (`body select`, `body textarea`) בכוונה: ה־preflight
של Tailwind נטען אחרי `styles.css` ומאפס `padding` על אלמנטים אלה, ורק
סלקטור בעוצמה גבוהה ממנו — ונמוכה ממחלקה — מחזיר לשדות את הריווח שלהם בלי
לדרוס את `.admin-menu-search input` ודומיו.

### זום, החלקה ומצגת בתצוגה המלאה

שלושה מודולים, בלי ספרייה חיצונית: `lightbox-math.js` (חשבון טהור, נבדק
ב־`lightbox-math.test.mjs`), `lightbox-gestures.js` (Pointer Events) ו־`lightbox-slideshow.js`.

- **זום**: צביטה בשתי אצבעות וגלגלת עם Ctrl/⌘ (כך גם צביטה במשטח מגע), 1x עד 5x
  סביב הנקודה שמתחת לאצבעות או לסמן. לחיצה כפולה או הקשה כפולה מחליפות בין 1x
  ל־2.5x סביב הנקודה. כשהתמונה מוגדלת גרירה (או גלגלת רגילה) מזיזה אותה, עד
  שקצה התמונה נוגע בקצה הבמה. עם ההגדלה הראשונה התמונה מתחלפת לקובץ המקורי
  (אחרי שנטען ופוענח), במקום התצוגה הבינונית. כל מעבר פריט מאפס את הזום. הזום
  וההזזה הם המאפיינים `scale` ו־`translate` של התמונה, ולא `transform`, כדי שלא
  יתנגשו באנימציית הכניסה ובתנועת המצגת. המצב מסומן ב־`data-zoom` וב־`.is-zoomed` על `#lightboxStage`.
- **החלקה (מגע)**: התמונה עוקבת אחרי האצבע; מעבר לפי מרחק (חמישית מרוחב הבמה)
  או הנפה מהירה, עם אנימציית יציאה וכניסה ורטט קצר (`navigator.vibrate`) כשנתמך.
  **הכיוון**: האתר מימין לשמאל, ולכן הפריט הבא יושב משמאל — כמו כפתור „התמונה
  הבאה” שבצד שמאל וחץ שמאלה במקלדת שמתקדם. גרירת האצבע **ימינה** מושכת אל הבמה
  את מה שמשמאל, כלומר עוברת **לבא**; גרירה שמאלה חוזרת לקודם. בקצוות הרשימה אין
  מעבר מעגלי בהחלקה — התמונה נמתחת כגומייה וחוזרת (החצים והמקלדת ממשיכים להתגלגל
  כמו קודם). משיכה למטה סוגרת. בזמן זום אין החלקה: הגרירה מזיזה את התמונה.
- **מצגת**: „הפעל מצגת” בסרגל התצוגה המלאה (`#slideshowToggle`), בסרגל הגלריה
  ובדף האירוע מנגן את התיקייה המוצגת: מסך מלא כשה־Fullscreen API זמין, עמעום בין
  השקופיות ותנועת Ken Burns איטית (עם `prefers-reduced-motion` — עמעום בלבד),
  3/5/8 שניות לשקופית (נשמר בדפדפן), פס התקדמות, וסרטונים שמתנגנים עד הסוף או
  מדולגים לפי בחירה. רווח משהה וממשיך, Escape (או יציאה ממסך מלא) עוצר — Escape
  נוסף סוגר את התצוגה. Wake Lock שומר על המסך דולק בזמן ניגון. המצב מסומן
  ב־`data-slideshow` על `#lightboxModal` ומוכרז לקוראי מסך ב־`#slideshowStatus`.

## מבנה לוח הניהול

הלוח הוא דשבורד: `ADMIN_VIEWS` שב־`admin-ui.js` היא המקור היחיד לתפריט,
לחיפוש, לסדר המסכים ולמוני ההתראות. לכל רשומה שם יש `section.admin-view`
אחד ויחיד ב־`admin.html`, והמעבר בין מסכים הוא החלפת המסך הפעיל בלבד.

הגרסה הקודמת עבדה אחרת: התוכן ישב ככרטיס אקורדיון בתפריט, ולחיצה **העבירה
את הרכיב עצמו** לתוך חלון משימה. משם הגיעו שתי התקלות שחזרו — אותו תוכן
שנראה פעמיים, וחלון שנפתח ריק כשהרכיב נשאר מאחור. אין יותר `adminTaskModal`
ואין `restoreAdminTaskContent`.

הוספת מסך היא שלושה צעדים: רשומה ב־`ADMIN_VIEWS`, `section` עם
`id="view-<id>"` ו־`data-view="<id>"` ב־`admin.html`, ובמידת הצורך טעינת
נתונים ב־`runViewHook`. הבדיקות `admin-menu-order.test.mjs` נועלות את
ההתאמה בין השניים, ובכללן שכל מסך מופיע בדיוק פעם אחת.

השמות הישנים `openAdminTaskWindow('accPending')` ו־`openAdminCategory('gallery')`
ממשיכים לעבוד ומפנים למסך המתאים.

## בניית גיליון הסגנון

העיצוב מורכב משני קבצים: `styles.css` בכתב יד, ו־`tailwind.generated.css`
שנבנה מראש. עד כה נטען במקומו `cdn.tailwindcss.com` — סקריפט חוסם־רינדור
שקימפל את כל ה־CSS בדפדפן בכל טעינה, וטיילווינד עצמם מגדירים אותו ככלי
פיתוח בלבד.

```bash
npm install       # פעם אחת
npm run build:css # אחרי כל שינוי במחלקות שב-HTML או ב-JS
```

הבנייה סורקת את `index.html` ואת קובצי ה־JS, משום שחלק ניכר מה־HTML נבנה
שם כמחרוזות. **חובה להריץ אותה ולהוסיף את הפלט ל־commit**; `npm run check:css`
רץ ב־CI ונכשל אם הפלט אינו מעודכן.

`tailwind.generated.css` נטען **אחרי** `styles.css`, ואין להחליף את הסדר:
ה־Play CDN הזריק את הסגנון שלו בסוף ה־`head` ולכן ה־utilities גברו על
`styles.css`. בסדר הפוך, למשל, `.admin-topic-card { display:flex }` היה גובר
על `hidden` וכפתורי מנהל־על היו נחשפים לכל מבקר.

## טעינת מודולים לפי צורך

`chat.js`, `face-search.js` ו־`face-index.js` אינם נטענים בפתיחת האתר. כל
נקודות הכניסה שלהם נמצאות מאחורי פעולה מפורשת, ולכן `defineLazyModule`
שב־`app.js` רושמת מעטפת בשם כל פונקציה: המטפל שב־HTML קורא לה, היא מושכת
את המודול בייבוא דינמי, והמודול דורס אותה בפונקציה האמיתית.

מבקר שאינו מחובר מוריד 348KB של JS במקום 460KB. משתמש מחובר כן מקבל את
`chat.js` — תג ההודעות שלא נקראו מצויר בפאנל הפרופיל בלי לפתוח חלון — אבל
דרך `refreshChatUI`, כלומר אחרי הציור הראשון ולא לפניו.

**בהוספת נקודת כניסה חדשה למודול עצל יש לרשום אותה ברשימה של
`defineLazyModule`**, אחרת המטפל שב־HTML יקרא לפונקציה שאינה קיימת עדיין.

`admin.js` ו־`drive-sync.js` נשארו בטעינה רגילה במכוון: `updateAdminOverview`
נקרא מכל רינדור של הגלריה, ו־`drive-sync.js` מחזיק גם את פונקציות ההתחברות
של Google ואינו מודול ניהול בלבד.

## הודעת הפופ-אפ

מנהל־על מעלה תמונה אחת שמוצגת למבקרים בכניסה לאתר, ובוחר לאן הלחיצה עליה
מפנה. מתחת לתמונה מוצג כפתור פעולה שנושא את שם היעד, כדי שהפנייה תהיה גלויה
ולא תסתמך על ניחוש שהתמונה לחיצה. הפופ-אפ נסגר לפני שהיעד נפתח, משום שהוא
יושב מעל שאר החלונות.

| יעד הפנייה | מה נפתח |

| ללא פנייה | רק התמונה, בלי כפתור פעולה |

ההרשאה נשארות במקום אחד: מי שאינו מאושר ולוחץ על פנייה לחיפוש פנים מקבל את
אותה הודעה שהיה מקבל מהכפתור הרגיל. רשימת הכלים מוגדרת ב־`POPUP_FEATURE_TARGETS`

שבלוח הניהול. הודעות שנשמרו לפני התוספת ממשיכות לעבוד כפי שהן.

## חיבור Cloudflare D1

1. ב־Cloudflare פתח **Storage & databases → D1 SQL database** וצור מסד בשם `simchas-gallery-db`.
2. פתח את המסד, עבור ל־**Console**, הדבק את תוכן `cloudflare-d1-schema.sql` והפעל אותו.
3. פתח את ה־Worker הקיים `simchas-gallery-api`.
4. תחת **Settings → Bindings** הוסף **D1 database binding** בשם המדויק `GALLERY_DB` ובחר את המסד שיצרת.
5. החלף את קוד ה־Worker בתוכן `cloudflare-worker.js` ופרוס.

יש להשאיר את חיבור R2 הקיים בשם `GALLERY_BUCKET`.

## שמירת ההתחברות

אסימון של Google תקף כשעה בלבד, ולכן הוא משמש רק לכניסה הראשונה. מיד אחריה
ה־Worker מנפיק אסימון התחברות משלו, חתום ב־HMAC ותקף שנה, והדפדפן שומר אותו
ב־`localStorage`. התוצאה: מי שהתחבר פעם אחת נשאר מחובר באותו דפדפן — גם אחרי
סגירת הלשונית, גם בלשוניות נוספות — עד שהוא מתנתק בעצמו.

התוקף מתגלגל: בכל ביקור שחל יותר מיממה אחרי הנפקת האסימון הדפדפן מחדש אותו
ברקע (`POST /auth/session` עם האסימון הקיים), ותאריך הפקיעה מתרחק שוב בשנה.
כך מי שנכנס לאתר ולו פעם בשנה אינו מנותק לעולם. הגרסה הקודמת הנפיקה אסימון
לשלושים יום וחידשה אותו רק בשבוע האחרון לתוקפו, ולכן מי שלא ביקר בדיוק באותו
שבוע נותק ונדרש להתחבר מחדש — זו הסיבה שהאתר "לא זכר משתמשים". אסימונים
שהונפקו בגרסה הקודמת מתחדשים מיד בביקור הבא ומקבלים את התוקף החדש.

ההתחברות נשמרת לכל מקור (origin) בנפרד, כדרך הדפדפנים: התקנה למסך הבית
ב־iPhone היא אחסון נפרד מ־Safari, וכניסה דרך כתובת אחרת של האתר היא התחברות
נפרדת. ב־Safari, אחסון של אתר שלא נעשתה בו שום פעולה במשך שבעה ימי שימוש
בדפדפן עשוי להימחק על ידי הדפדפן עצמו (ITP), וזה אינו בשליטת האתר.

ההרשאות נקראות מהמסד בכל בקשה, ולכן חסימה או שינוי דרגה של משתמש נכנסים לתוקף
מיד, גם אם האסימון שבידיו עדיין תקף.

שינוי הערך של `SESSION_SIGNING_SECRET`, או מחיקת הטבלה `auth_secrets`, מבטל את
כל אסימוני ההתחברות הקיימים ומחייב את כל המשתמשים להתחבר מחדש.

## שכבת הנתונים: סינון, סמני דפדוף, ETag ומטמון קצה

כל אוסף נשמר בטבלה אחת, `gallery_documents`, כמסמך JSON לכל שורה. ה־API
של `/data/<אוסף>` מאפשר לבקש ממנה בדיוק את מה שצריך, במקום את האוסף כולו.

### סינון וספירה ב־SQL

| בקשה | מחזירה |
|---|---|
| `GET /data/<אוסף>?folderId=<id>` | רק מסמכים ששדה `folderId` שלהם שווה לערך. הסינון רץ ב־D1 (`json_extract`), לא בדפדפן |
| `GET /data/<אוסף>?ids=a,b,c` | רק המסמכים שמזהיהם ברשימה (עד 200 בבקשה). משמש לתצוגת המועדפים ולתוצאות חיפוש הפנים |
| `GET /data/<אוסף>/count?folderId=<id>` | `{success, count}` — מספר המסמכים שעונים לסינון, בלי להוריד אותם |
| `GET /data/<אוסף>/counts?by=folderId` | `{success, by, total, counts: {"<ערך>": n}}` — מונים מקובצים בשאילתה אחת. כך מתמלאים מוני התיקיות ומספרי הפוסטר |

השדות שאפשר לסנן ולקבץ לפיהם סגורים ברשימה `DATA_FILTER_FIELDS` שב־Worker:
`folderId`, `status`, `mediaType`, `uploadedBy`. שם שדה אחר בכתובת מתעלמים ממנו
(סינון) או נדחה (קיבוץ), ולכן שום מחרוזת מהכתובת אינה נכנסת לשאילתה כמות שהיא.
ערך ההשוואה עובר `CAST … AS TEXT`, כך שמזהה תיקייה שנשמר כמספר בגיבוי ישן
עדיין מתאים לערך מהכתובת. ההרשאות זהות לאלה של רשימת האוסף: צופה ממתין אינו
יכול לספור תמונות, וצופה מאושר אינו יכול לספור משתמשים.

בדפדפן, `where('folderId', '==', id)` ב־`getDocs`/`getDocsPage` הופך לפרמטר
הזה, ו־`where('id', 'in', [...])` ל־`?ids=`. נוספו גם `getCount`, `getCounts`
ו־`getDocsByIds` ב־`cloudflare-client.js` (וב־`window.firestoreModules`).

### סמני דפדוף במקום OFFSET

רשימה ממוינת לפי שדה עם ערכים חוזרים (למשל `createdAt` של תמונות שסונכרנו
יחד) אינה יציבה תחת `OFFSET`: כתיבה בין עמוד לעמוד מזיזה את כל השורות, ואותה
שורה חוזרת פעמיים או נעלמת. לכן כל עמוד מחזיר `nextCursor` — JSON ב־base64url
של ערך המיון ומזהה השורה האחרונה, `{v, id}` — והעמוד הבא מתבקש עם
`?after=<cursor>`. השאילתה ממשיכה מהמקום המדויק בהשוואת צמד, שנכתבת כ־`OR`
מפורש כי תמיכת D1 בהשוואת שורות אינה מובטחת:

```sql
WHERE collection_name = ?
  AND (CAST(COALESCE(json_extract(data_json, '$.createdAt'), 0) AS REAL) < ?
       OR (CAST(…) = ? AND document_id > ?))
ORDER BY CAST(…) DESC, document_id ASC
LIMIT ? -- limit + 1: השורה הנוספת אומרת אם יש המשך
```

`nextCursor` הוא `null` בעמוד האחרון. `offset` ממשיך לעבוד למי שעדיין משתמש בו,
אך כשנשלח `after` הוא מתעלם ממנו. `getDocs` בדפדפן עוקב אחרי הסמנים בעצמו,
ומול Worker ישן שאינו מחזיר סמן חוזר ל־`OFFSET` כבעבר.

### ETag ותשובות 304

כל תשובת `GET` מוצלחת מ־`/data/…` — מסמך, רשימה או מונה — נושאת `ETag` חזק:
SHA-256 של הגוף, base64url, 22 התווים הראשונים. הדפדפן שומר בזיכרון עד 200
תשובות אחרונות לפי כתובת, שולח `If-None-Match` בבקשה החוזרת, ומקבל `304`
ריק כשהנתונים לא השתנו — חוסך את הגוף, לא את הבדיקה. כך רענון הגלריה
בחזרה ללשונית עולה כמה מאות בתים במקום את כל הרשימה. `If-None-Match` רשומה
ב־`Access-Control-Allow-Headers` ו־`ETag` ב־`Access-Control-Expose-Headers`;
בלעדיהן הדפדפן היה חוסם את הבקשה המותנית כבר ב־preflight. Cloudflare דוחס
את ה־JSON בקצה בעצמו, ולכן אין כאן דחיסה ידנית.

### מטמון קצה וגרסאות נתונים

רשימות ומונים נשמרים ב־Cache API של Workers (`caches.default`) לחמש דקות
(`s-maxage=300` על העותק השמור בלבד; לדפדפן התשובה נשארת `no-store`).
המפתח הסינתטי מורכב מהאוסף, ממחרוזת השאילתה המנורמלת, מ**גרסת הנתונים** של
האוסף וממחלקת ההרשאה של המבקש (`approved-viewer` / `admin` / `super_admin`) —
**ולעולם לא ממזהה המשתמש**: כל הצופים המאושרים חולקים עותק אחד של כל רשימה.
אוספים אישיים (`userFavorites`, `userPreferences`) ומסמכים בודדים אינם נכנסים
למטמון. העותק השמור מכיל גוף ו־`ETag` בלבד, בלי כותרות CORS, והן נבנות לכל
בקשה לפי מקורה; לכן גם תשובת `304` מתוך המטמון נכונה.

גרסת הנתונים נשמרת ב־`gallery_schema_meta` תחת `data_version:<אוסף>`
ומתקדמת בכל כתיבה לאוסף — `PUT`/`DELETE` ב־`/data`, העלאה (`/upload`), אישור
(`/approve`), מחיקת קובץ (`/media`), כתיבת פרופיל בכניסה, הגירת פרופיל ישן
והודעות צ׳אט (שיושבות ב־`userProfiles`). הגרסה החדשה היא הגדול מבין "הקודמת + 1"
ו־`Date.now()`, כך שהיא עולה תמיד ואינה חוזרת לערך ישן גם אחרי איפוס הטבלה.
קריאת הגרסה היא שאילתת מפתח אחת ב־D1 לכל בקשת רשימה, והתוצאה: כתיבה מפילה את
המטמון מיד, ורשימה שלא השתנתה מוגשת מהקצה בלי לגעת ב־D1.

**מה יש להגדיר ידנית:** Cache API פעיל רק ב־Worker שמוגש מדומיין שבחשבון
Cloudflare. בכתובת `*.workers.dev` — שבה ה־Worker רץ היום — פעולות `match`
ו־`put` מתעלמות בשקט, והקוד ממשיך בלעדיהן (ETag וסמני הדפדוף פועלים בכל מקרה).
כדי ליהנות מהמטמון יש לחבר ל־Worker דומיין מותאם (למשל `api.<הדומיין>`) דרך
**Workers & Pages → simchas-gallery-api → Settings → Domains & Routes**, ולעדכן
את הכתובת ב־`api-environment.js`.

### הגלריה נטענת לפי תיקייה

עד היום דף הגלריה הוריד את כל אוסף התמונות בכניסה, בכל רענון (15 דקות) ובכל
חזרה ללשונית. עכשיו, ב־`gallery-feed.js`:

- `state.images` מחזיק רק את התיקייה הפעילה. בכניסה נטען העמוד הראשון של "כל
  הארכיון" — 120 החדשות ביותר (`orderBy=createdAt&direction=desc&limit=120`).
  מעבר תיקייה מבקש את העמוד הראשון שלה (`folderId=`), ולכל תיקייה יש מטמון
  בזיכרון לאורך הביקור, כך שחזרה אליה מיידית.
- `window.loadMoreImages()` מביא את העמוד הבא של התיקייה הפעילה בסמן הדפדוף
  ומחזיר `{added, done}`; `window.state.imagesHasMore` אומר אם נשארו עמודים.
  הגלילה מציירת רק את המנות שכבר בזיכרון; הכפתור **טען פריטים ישנים יותר**
  בתחתית הגלריה הוא שפונה לענן. חיפוש בתיקייה שטרם נטענה כולה מושך את שאר
  העמודים ברקע, כדי שהתוצאות יכסו גם פריטים ישנים.
- מוני התיקיות, המונים שבפוסטר ו"כל הארכיון" מגיעים משאילתה אחת:
  `GET /data/images/counts?by=folderId`.
- פסיפס הכניסה, "חדש מאז הביקור הקודם" וההתראה על פריטים חדשים בתיקיות
  שבמעקב משתמשים בשאילתת "החדשות ביותר" קטנה (`limit=24`), לא ברשימה המלאה.
- המועדפים נטענים לפי מזהים (`?ids=`), ותוצאות חיפוש הפנים שאינן בתיקייה
  הטעונה נמשכות באותה דרך.
- ניקוי התיקיות הריקות (מנהל־על) נשען על המונים מהשרת ולא על מה שבזיכרון —
  אחרת כל תיקייה שלא נטענה הייתה נראית ריקה.

דף הניהול אינו משתמש במודול הזה: הסטטיסטיקה, הגיבוי, סנכרון Drive ואינדוקס
הפנים צריכים את הרשימה כולה, ולכן רק הוא ממשיך להוריד את כל האוסף — בעמודים
של 1,000, עם סמני דפדוף.

## ניטור שגיאות

האתר וה־Worker מדווחים על תקלות לטבלה `client_errors` ב־D1, ולוח הניהול
מציג אותן במסך **שגיאות ותקלות** (`admin.html#errors`). הרשומות מקובצות לפי
טביעת אצבע — SHA-256 של המקור, ההודעה והשורה הראשונה במחסנית, בלי מספרי
שורה — ולכן כל סוג תקלה הוא שורה אחת עם מונה מופעים, ולא יומן שגדל בלי גבול.

### מה נאסף

| שדה | תוכן |
|---|---|
| `message`, `stack` | הודעת השגיאה והמחסנית, עד 500 ועד 4,000 תווים |
| `url` | כתובת הדף שבו אירעה השגיאה, עד 500 תווים |
| `user_agent` | מחרוזת הדפדפן, עד 300 תווים |
| `last_uid` | מזהה המשתמש המחובר האחרון שנתקל בתקלה — רק כשהדיווח נשא אסימון תקף |
| גרסת האתר, קוד השגיאה, המסלול | בבלוק "הקשר" שבסוף המחסנית |

לא נשמרים שם, כתובת דוא״ל או תוכן אישי. כל טקסט מנוקה לפני השמירה: כותרות
`Bearer`, אסימוני ההתחברות של האתר, אסימוני Google ופרמטרים כמו `id_token`
בכתובת מוחלפים ב־`[הוסר]`, וכל כתובת דוא״ל מוחלפת ב־`[דוא״ל הוסר]`.

### מה הדפדפן שולח

`error-monitor.js` נטען בכל דף ומאזין ל־`error` ול־`unhandledrejection`. קוד
שתופס שגיאות בעצמו קורא ל־`window.reportClientError(error, 'scope')` — כך
מדווחים כישלון התחברות, כישלון העלאה, שגיאות ממאזיני הנתונים וכשלונות חיפוש
הפנים והאינדוקס. הכללים: אותה שגיאה נשלחת פעם אחת לכל טעינת דף, עד עשר
שגיאות שונות לטעינה, ורעש ידוע אינו נשלח כלל — `ResizeObserver loop`,
`Script error.` ממקור אחר, בקשות שבוטלו ושגיאות בזמן ניתוק מהרשת.

משתמש מחובר מדווח ב־`fetch` עם האסימון, כדי שהשרת ירשום מי נתקל בתקלה;
מי שאינו מחובר מדווח ב־`navigator.sendBeacon` עם Blob של JSON, או ב־`fetch`
עם `keepalive` כשאין `sendBeacon`.

לכל דיווח מצורפת גרסת האתר: הקבוע `SITE_VERSION` שב־`app.js`. אין לקוד
גישה ל־git, ולכן הערך חייב להיות זהה ל־`CACHE_VERSION` שב־`sw.js` ולעלות
יחד איתו בכל פריסה; `error-monitor.test.mjs` נכשל כשהשניים אינם תואמים.

### מה ה־Worker רושם

כשבקשה נכשלת בשגיאה פנימית (סטטוס 500 ומעלה) ה־Worker רושם אותה בעצמו עם
`source: worker`, השיטה והנתיב; תשובות 4xx — חוסר הרשאה, קלט שגוי — אינן
תקלה ואינן נרשמות. הרישום רץ אחרי שהתשובה יצאה (`ctx.waitUntil`) ולעולם אינו
משנה אותה, גם כשהמסד עצמו אינו זמין.

### מגבלות

- 30 דיווחים לשעה לכל כתובת IP; מעבר לכך `429`.
- דיווח מתקבל עם אסימון או בלעדיו; אסימון פסול אינו דוחה את הדיווח, רק
  משאיר את `last_uid` ריק.
- דיווח לא תקין נענה ב־`400`, וכישלון שמירה נענה ב־`{ success: true, stored: false }`
  — יומן השגיאות לעולם אינו מפיל את הדפדפן שדיווח.

### טיפול בלוח הניהול

מנהל (דרגה 3 ומעלה) רואה במסך את השגיאות הפתוחות: הודעה, מקור (האתר או
השרת), מספר מופעים, מתי נראתה לראשונה ולאחרונה, המשתמש האחרון וכתובת הדף;
לחיצה על ההודעה פותחת את המחסנית. התג שבתפריט ושורת "ממתין לטיפול" בסקירה
מציגים כמה שגיאות פתוחות נראו ביממה האחרונה. מנהל־על מסמן **טופל**, מחזיר
עם **פתח מחדש**, ומנקה בלחיצה אחת שגיאות שטופלו לפני יותר משלושים יום.
שגיאה שסומנה כטופלה ונרשמה שוב חוזרת מאליה לרשימה הפתוחה — זה האות שהתיקון
לא הספיק.

### נקודות הקצה

| נתיב | הרשאה | תפקיד |
|---|---|---|
| `POST /telemetry/errors` | כל אחד, מוגבל בקצב | דיווח שגיאה: `{ message, stack, url, userAgent, extra? }`; עונה `{ success: true }` |
| `GET /telemetry/errors?status=open\|resolved&limit=` | מנהל או מנהל־על | רשימת השגיאות, מהמופע האחרון לישן |
| `GET /telemetry/errors/summary` | מנהל או מנהל־על | `{ open, last24h }` לתג שבתפריט |
| `POST /telemetry/errors/resolve` | מנהל־על | `{ fingerprint }` — סימון כטופלה |
| `POST /telemetry/errors/reopen` | מנהל־על | `{ fingerprint }` — פתיחה מחדש |
| `POST /telemetry/errors/clear` | מנהל־על | מחיקת שגיאות שטופלו לפני יותר משלושים יום |
## בדיקות דפדפן אוטומטיות

לצד בדיקות היחידה (`npm test`) רצה בכל PR, במשימה `e2e` שב־`checks.yml`,
חבילת בדיקות קצה־לקצה ב־Playwright: Chromium אמיתי טוען את `index.html` ואת
`admin.html` משרת סטטי מקומי (`e2e/static-server.mjs`) ובודק את מה שהמבקר
רואה בפועל — שער הכניסה, שחזור ההתחברות מאסימון שמור (גם בלשונית נוספת),
כניסה דרך Google והחלפת האסימון באסימון השרת, התנתקות, מסכי ממתין / נדחה /
חסום, ציור הגלריה, התצוגה המלאה ולוח הניהול. בדיקה נכשלת גם אם הדף זרק
שגיאה (`pageerror`) בדרך, ולכן רגרסיה שקטה בקוד הדף נתפסת לפני הפריסה.

הבדיקות אינן נוגעות ברשת וב־Worker האמיתי. `e2e/fixtures.mjs` מיירט את
הבקשות של הדפדפן: ספריית Google Identity, lucide והגופנים מוחלפים בתחליפים
קטנים, וה־Worker מוחלף בזיוף בזיכרון שמחזיר בדיוק את הצורות
ש־`cloudflare-client.js` מצפה להן — `POST /auth/session`,
`GET/PUT/DELETE /data/<אוסף>/<מזהה>` עם עימוד ומיזוג, כותרות CORS, שגיאות
401/403/404 וכללי ההרשאה של `assertDataPermission`. הנתונים (פרופיל, תיקיות,
תמונות) נזרעים בכל בדיקה בנפרד, ואסימון ההתחברות המזויף נכתב ל־`localStorage`
בדיוק כפי שדפדפן של משתמש מחובר מכיל אותו. ה־Service Worker חסום בבדיקות,
כדי שהקוד יגיע תמיד מהשרת ולא מהמטמון.

```bash
npm install                         # פעם אחת
npx playwright install chromium     # פעם אחת: הורדת הדפדפן
npm run test:e2e                    # כל הבדיקות, ללא חלון
npx playwright test --headed        # עם חלון דפדפן
npx playwright test e2e/admin.spec.mjs   # קובץ בודד
```

השרת הסטטי מאזין ב־`127.0.0.1:8080`; אם הפורט תפוס, `E2E_PORT=8123 npm run test:e2e`.
אותן בדיקות רצות גם על תוצר הבנייה: `npm run build && E2E_ROOT=dist npm run test:e2e`
(השרת מגיש אז את `dist/` באותם נתיבים). ב־CI שתי הריצות מתבצעות בכל PR.
בכישלון נשמרים צילום מסך ו־trace תחת `test-results/`, וב־CI הם מצורפים לריצה
כ־artifact. `node --test` אינו מריץ את קובצי `e2e/*.spec.mjs`, ולהפך.

## עדכון כפוי: גרסה חדשה מרעננת את הדף מיד

משתמש שהאתר פתוח אצלו אינו צריך לרענן בעצמו אחרי פריסה. `auto-update.js`
נטען בשני הדפים ועושה שלושה דברים:

1. **מזהה פריסה חדשה.** `version.json` נושא front matter, ולכן Jekyll של
   GitHub Pages ממלא בו בכל פריסה את זמן הבנייה (`site.time`) ואת ה־commit
   (`site.github.build_revision`). הדף טוען אותו בכניסה (`cache: no-store`),
   שומר את תוכנו ב־`window.SITE_BUILD`, ובודק שוב כל דקה כשהלשונית גלויה, בכל
   חזרה ללשונית, במיקוד ובחזרת הרשת. תוכן שונה = גרסה חדשה. בשרת שאינו מריץ
   Jekyll (למשל בבדיקות) הקובץ נשאר לא מעובד, ואז הבדיקה נופלת ל־`ETag` של
   `index.html`. Service Worker חדש שתופס שליטה בדף מפעיל את אותו מסלול.
   באתר הבנוי (`npm run build`, ראו "פריסה") אין Jekyll: `version.json`
   נכתב בזמן הבנייה עם אותו מבנה בדיוק — `revision` מ־`GITHUB_SHA` ו־`builtAt`
   משעת הבנייה — ולכן כל פריסה עדיין מזוהה כגרסה חדשה.
2. **מרענן מיד כשאפשר.** לשונית מוסתרת מתרעננת בשקט; לשונית פעילה מתרעננת
   מיד — אלא אם המשתמש באמצע העלאה (`window.markSiteBusy('upload')`), הקלדה
   בשדה שיש בו טקסט, או צפייה בסרטון. אז מופיעה הודעה אחת והרענון מתבצע
   ברגע שהפעולה מסתיימת (בדיקה כל חמש שניות). פעולה ארוכה אחרת מסמנת את עצמה
   ב־`window.markSiteBusy(סיבה)` ומנקה ב־`window.clearSiteBusy(סיבה)`.
3. **מביא באמת את הקוד החדש.** ה־Service Worker מבקש כל קובץ קוד עם
   `cache: no-cache`, כלומר מאמת אותו מול השרת (304 כשאין שינוי) במקום לסמוך
   על עשר הדקות של ה־HTTP cache של GitHub Pages; כך רענון אחרי פריסה אינו
   מקבל עוד קוד ישן מהמטמון. `version.json` עצמו אינו עובר דרך המטמון כלל.

הגנה מלולאה: הגרסה שבגללה רוענן הדף נשמרת ב־`sessionStorage`, ואם אחרי
הרענון השרת עדיין מגיש את הגרסה הקודמת (CDN שטרם התעדכן), אין רענון נוסף
בשתי הדקות הקרובות. `window.checkForSiteUpdate()` מפעיל בדיקה מיידית.

## פריסה

האתר מתפרסם אוטומטית מ־GitHub Pages לאחר עדכון ענף `main` (מקובצי המקור, או
מתוצר הבנייה של Vite אחרי המעבר — ראו "בניית ייצור ב־Vite" להלן). גם ה־Worker נפרס
אוטומטית באמצעות `.github/workflows/deploy-worker.yml` בכל שינוי של
`cloudflare-worker.js`: ענף `main` אל Worker הייצור, וענף `staging` אל
`simchas-gallery-api-staging` של סביבת הניסוי (ראה "סביבת ניסוי" להלן).
לפני ההפעלה הראשונה יש להגדיר ב־GitHub,
תחת **Settings → Secrets and variables → Actions**, סוד אחד בלבד:

| סוד | ערך |
|---|---|
| `CLOUDFLARE_API_TOKEN` | אסימון Cloudflare בעל הרשאת Workers Scripts:Edit |

הפריסה קוראת את שמות כל ה־Bindings מהגרסה הפעילה ומורישה אותם לגרסה החדשה.
לפני העלאה היא מוודאת ש־`GALLERY_DB` ו־`GALLERY_BUCKET` קיימים, ולכן אינה
יוצרת מסד או דלי חדשים ואינה זקוקה למזהים שלהם ב־GitHub. לאחר הפריסה מתבצעת
בדיקת `/health` שמוודאת כי D1 ו־R2 מחוברים ושה־Worker מדווח על הסביבה
המצופה. אפשר גם להפעיל פריסה ידנית מתוך **Actions → Deploy Cloudflare Worker →
Run workflow** ולבחור בשדה `target` לאן לפרוס: `production` רץ מ־`main` בלבד,
ו־`staging` מותר מכל ענף.

לפני מעבר סופי מומלץ להוריד גיבוי JSON ממסך הגיבוי שבלוח הניהול, ולאחר חיבור D1 לשחזר אותו דרך מסך הגיבוי באתר. קובצי המדיה עצמם נשארים ב־R2.

### בניית ייצור ב־Vite והמעבר לפריסה מ־GitHub Actions

`npm run build` בונה את האתר ב־Vite לתיקייה `dist/` (שאינה נשמרת במאגר): שני
הדפים (`index.html`, `admin.html`) עם JS ו־CSS מאוגדים, מוקטנים ובשמות מגובבים
תחת `assets/`, ובסיס יחסי (`base: './'`) כך שהתוצר עובד תחת `/1/` בלי לקבע את
שם המאגר. התוסף `site-build.mjs` משלים את מה ש־Vite אינו עושה לבד:

- מעתיק כמות שהם את `sw.js`, `manifest.webmanifest`, הסמלים ו־`admin-messages.html`.
- כותב מחדש את `APP_SHELL` שב־`dist/sw.js` ממניפסט הבנייה של Vite: דף הגלריה,
  ה־CSS וה־JS שהוא טוען (בשמות המגובבים) והסמלים. מודולי הניהול נשארים בחוץ
  כמו במקור. `CACHE_VERSION` אינו משתנה, וממשיך לעלות יחד עם `SITE_VERSION`.
- כותב `dist/version.json` אמיתי (commit וזמן בנייה) ו־`dist/.nojekyll`.

קובצי המקור אינם משתנים ואין צורך בבנייה כדי לעבוד: `npm run dev` מריץ את שרת
הפיתוח של Vite, `npm run preview` מגיש את `dist/` אחרי בנייה, ושרת סטטי פשוט על
שורש המאגר ממשיך לעבוד כמו קודם.

**הפריסה.** `.github/workflows/pages.yml` רץ בכל דחיפה ל־`main`: `npm ci`, בדיקת
תחביר, `npm test`, `npm run build`, והעלאת `dist/` ל־GitHub Pages
(`upload-pages-artifact` + `deploy-pages`). שלב הפריסה פועל **רק** כשמקור
Pages הוא GitHub Actions; עד אז הוא מדלג (עם הודעה בריצה), והאתר ממשיך להיות
מוגש מקובצי המקור שבענף `main` דרך Jekyll — בדיוק כמו היום. לכן שני המסלולים
עובדים במקביל, ואין למחוק את קובצי המקור או את ה־front matter של `version.json`.

**המעבר (פעולה אחת של בעל המאגר):**

1. **Settings → Pages → Build and deployment → Source** → לבחור **GitHub Actions**.
2. **Actions → Deploy site to GitHub Pages → Run workflow** (או לדחוף ל־`main`).
   מעכשיו כל דחיפה ל־`main` בונה ופורסת את `dist/`.

**חזרה לאחור:** באותו מסך לבחור שוב **Deploy from a branch** עם `main` ו־`/ (root)`
ולשמור. GitHub Pages חוזר להגיש את קובצי המקור מהענף, ו־`pages.yml` חוזר לדלג
על שלב הפריסה. אין צורך לשנות קוד בשום כיוון.

אתר הניסוי ב־Cloudflare Pages (ענף `staging`) אינו מושפע ומוגש כמו קודם מקובצי
המקור, בלי בנייה.

### הבדיקה האדומה של Workers Builds — אין לתקן אותה בהוספת wrangler.jsonc

בכל PR מופיעה בדיקה כושלת בשם `Workers Builds: simchas-gallery-api`. היא אינה
נובעת מהקוד ואינה חוסמת מיזוג: מקורה בשילוב ה־Git של Cloudflare Workers Builds,
שמחובר למאגר ומריץ `npx wrangler deploy` בכל דחיפה. במאגר אין `wrangler.jsonc`,
ולכן הריצה נכשלת מיד. הכשלון הזה קיים בכל commit — למשל ב־#47, שנגע רק
ב־`cloudflare-client.js` ומוזג כך.

**הפתרון אינו הוספת קובץ `wrangler.jsonc`.** `wrangler deploy` מוחק כל Binding
שמוגדר בדשבורד ואינו מוצהר בקובץ ההגדרות, ו־`keep_vars` מכסה משתנים בלבד ולא
חיבורי D1 ו־R2. קובץ כזה היה הופך בדיקה אדומה בלתי מזיקה למפגע אמיתי: פריסה של
ה־Worker מכל ענף ומכל PR, ומחיקת `GALLERY_DB` ו־`GALLERY_BUCKET` בכל פעם שהמזהים
בקובץ אינם מדויקים. הכשלון הנוכחי הוא למעשה מה שמונע את זה.

הפריסה הנכונה כבר קיימת — `deploy-worker.yml`, שיורש את ה־Bindings מהגרסה הפעילה
(`bindings_inherit=strict`), רץ רק על `main` ועל `staging`, ורק כששונה `cloudflare-worker.js`.
לכן הדרך לסגור את הבדיקה היא **לנתק את שילוב ה־Git**, בדשבורד של Cloudflare:
**Workers & Pages → simchas-gallery-api → Settings → Build → Disconnect repository**.
פעולה זו אינה נוגעת ב־Worker הפעיל, ב־Bindings או בפריסה דרך ה־Action.

מאותה סיבה, גם את ה־Worker של סביבת הניסוי (`simchas-gallery-api-staging`) אין
לחבר ל־Git: שני ה־Workers נפרסים אך ורק דרך `deploy-worker.yml`.

## סביבת ניסוי (Staging)

שינוי גדול נבדק קודם בסביבה נפרדת לגמרי, שאינה נוגעת במשתמשים ובנתונים
האמיתיים: Worker משלה (`simchas-gallery-api-staging`) עם D1 ו־R2 משלו, ואתר
משלה שמוגש מ־Cloudflare Pages מתוך הענף `staging`. אותו קוד בדיוק רץ בשני
המקומות; ההבדל היחיד הוא ה־Bindings והמשתנים של כל Worker.

| | ייצור | ניסוי |
|---|---|---|
| אתר | `https://shmuel-lamed.github.io/1/` (GitHub Pages, ענף `main`) | `https://<project>.pages.dev` (Cloudflare Pages, ענף `staging`) |
| Worker | `simchas-gallery-api` | `simchas-gallery-api-staging` |
| כתובת ה־API | `https://simchas-gallery-api.0534169095.workers.dev` | `https://simchas-gallery-api-staging.0534169095.workers.dev` |
| D1 | `simchas-gallery-db` | `simchas-gallery-db-staging` (שם מומלץ) |
| R2 | הדלי הקיים | `simchas-gallery-media-staging` (שם מומלץ) |
| `ENVIRONMENT` | חסר (= `production`) | `staging` |

שמות המסד והדלי של הניסוי הם המלצה בלבד; מה שחייב להיות מדויק הוא שמות
ה־Bindings ב־Worker — `GALLERY_DB` ו־`GALLERY_BUCKET` — בדיוק כמו בייצור.

### איך האתר יודע לאן לפנות

`api-environment.js` הוא המקום היחיד שבו כתובת ה־Worker נקבעת;
`cloudflare-client.js`, `app.js`, `drive-sync.js` ו־`face-search.js` מייבאים
אותה משם. סדר ההחלטה:

1. ‎`?api=production` או ‎`?api=staging` בכתובת גובר על הכול, ונשמר
   ב־`sessionStorage` כך שהבחירה מחזיקה לאורך הלשונית, גם במעבר ללוח הניהול.
   ‎`?api=auto` מוחק אותה, וסגירת הלשונית מאפסת אותה ממילא. כך אפשר לפתוח את
   אתר הניסוי מול נתוני הייצור כדי להשוות, או את האתר הרגיל מול ה־Worker של
   הניסוי.
2. אתר שמוגש מ־`*.pages.dev` או מ־`localhost` / `127.0.0.1` פונה ל־Worker של הניסוי.
3. כל השאר — GitHub Pages והדומיין — פונה לייצור.

הסביבה הפעילה נחשפת ב־`window.API_ENVIRONMENT` (`production` או `staging`),
מסומנת על `<html data-api-environment>`, מוצגת כרצועת **סביבת ניסוי** בקצה
הכותרת כשהאתר פונה לניסוי, ומופיעה בדוח התקינות שבלוח הניהול.

ה־Worker מצדו מחזיר את הסביבה שלו ב־`GET /health` (`environment`), ומרשה
ב־CORS את `https://<project>.pages.dev` ואת פריסות התצוגה המקדימה
`https://<hash>.<project>.pages.dev` (לפי `STAGING_PAGES_PROJECT`, בבדיקת
סיומת על המארח ולא בביטוי רגולרי); מקורות `localhost` מורשים רק
כש־`ENVIRONMENT=staging`.

### הגדרה חד־פעמית (בדשבורד, פעם אחת)

**1. ה־Worker של הניסוי**

1. **Workers & Pages → Create → Create Worker**, בשם המדויק
   `simchas-gallery-api-staging`. פרוס את "Hello World" שמוצע — הקוד האמיתי
   יגיע מה־Action. אל תחבר את ה־Worker הזה ל־Git (ראה סעיף הבדיקה האדומה).
2. **Storage & databases → D1** → צור מסד `simchas-gallery-db-staging`, פתח
   **Console**, הדבק את תוכן `cloudflare-d1-schema.sql` והפעל.
3. **R2** → צור דלי `simchas-gallery-media-staging`.
4. ב־Worker החדש, **Settings → Bindings**: D1 binding בשם `GALLERY_DB` אל המסד
   החדש, ו־R2 binding בשם `GALLERY_BUCKET` אל הדלי החדש. **ודא פעמיים שלא
   נבחרו המסד או הדלי של הייצור.**
5. **Settings → Variables and Secrets** — לפי הטבלה:

| שם | ערך בניסוי | הערות |
|---|---|---|
| `ENVIRONMENT` | `staging` | חובה. בלעדיו ה־Worker נחשב לייצור, ובדיקת `/health` שבסוף הפריסה נכשלת |
| `STAGING_PAGES_PROJECT` | שם פרויקט ה־Pages | רשות; ברירת המחדל `simchas-gallery-staging`. חייב להתאים לשם שנבחר בשלב 2 |
| `GOOGLE_CLIENT_ID` | כמו בייצור | אותו לקוח OAuth משרת את שני האתרים |
| `GOOGLE_DRIVE_CLIENT_ID`, `GOOGLE_DRIVE_CLIENT_SECRET` | כמו בייצור | אותו לקוח Drive, עם כתובת החזרה נוספת (שלב 3) |
| `GOOGLE_DRIVE_REDIRECT_URI` | `https://simchas-gallery-api-staging.0534169095.workers.dev/drive/oauth/callback` | כתובת החזרה של ה־Worker של הניסוי |
| `GOOGLE_DRIVE_SITE_URL` | `https://<project>.pages.dev/` | לאן חוזרים אחרי חיבור Drive |
| `PUBLIC_API_ORIGIN` | **להשאיר ריק** | אחרת כתובות המדיה שמועלות בניסוי יצביעו על הייצור |
| `OPENAI_API_KEY`, `RESEND_API_KEY`, `EMAIL_FROM` | לפי הצורך | אפשר להשאיר ריקים: חיפוש AI ודוא״ל פשוט לא יעבדו בניסוי |
| `FACE_INDEX_TOKEN` | רשות | כמו בייצור, רק אם תהליך אינדוקס חיצוני רץ מול הניסוי |
| `SESSION_SIGNING_SECRET` | **לא להעתיק מהייצור** | להשאיר ריק: ה־Worker מייצר מפתח משלו ושומר אותו ב־D1 של הניסוי. כך אסימון התחברות של הניסוי אינו תקף בייצור, ולהפך |

**2. אתר הניסוי (Cloudflare Pages)**

1. **Workers & Pages → Create → Pages → Connect to Git**, ובחר את המאגר `SHMUEL-LAMED/1`.
2. **Project name**: `simchas-gallery-staging` (או שם אחר — ואז יש להגדיר `STAGING_PAGES_PROJECT`).
3. **Production branch**: `staging`. **Build command**: ריק. **Build output directory**: `/`.
4. **Save and Deploy**. הכתובת: `https://<project>.pages.dev`. כל ענף אחר שנדחף
   למאגר מקבל פריסת תצוגה מקדימה `https://<hash>.<project>.pages.dev` (אפשר
   לצמצם זאת ב־**Settings → Builds & deployments → Preview branches**).

**3. Google**

1. ב־Google Cloud Console → **Credentials**, בלקוח ה־OAuth של האתר
   (`GOOGLE_CLIENT_ID`), הוסף תחת **Authorized JavaScript origins** את
   `https://<project>.pages.dev` (ו־`http://localhost:<port>` לפיתוח מקומי).
   Google אינה מקבלת כוכבית, ולכן ההתחברות עובדת רק בכתובת הראשית של
   הפרויקט ולא בכתובות התצוגה המקדימה.
2. בלקוח ה־Drive (`GOOGLE_DRIVE_CLIENT_ID`), הוסף תחת **Authorized redirect URIs**
   את `https://simchas-gallery-api-staging.0534169095.workers.dev/drive/oauth/callback`.

**4. GitHub**

1. הסוד `CLOUDFLARE_API_TOKEN` הקיים משרת גם את הניסוי אם היקפו הוא
   **Account → Workers Scripts: Edit** לכל החשבון. אם האסימון הוגבל ל־Worker
   מסוים, יש להרחיב אותו או ליצור אסימון חדש ולעדכן את הסוד.
2. אחרי מיזוג השינוי הזה ל־`main`, צור את הענף: `git push origin main:staging`.
   הדחיפה הראשונה מפעילה את `deploy-worker.yml` עם היעד `staging`; הריצה
   מצליחה רק אם `/health` של הניסוי מחזיר `environment: "staging"` עם D1
   ו־R2 מחוברים (דלי ריק תקין).
3. היכנס לאתר הניסוי עם חשבון מנהל־העל. חשבונות מנהל־העל ההתחלתיים מזוהים
   לפי כתובת הדוא״ל גם בניסוי, ולכן הכניסה הראשונה כבר מגיעה כמנהל־על.

### נתונים לניסוי

סביבת הניסוי מתחילה ריקה, ושום דבר אינו מועתק אליה אוטומטית. כדי לעבוד מול
עותק של נתוני הייצור משתמשים במסך **גיבוי ושחזור** שבלוח הניהול (מנהל־על
בלבד):

1. באתר הייצור: **לוח הניהול → גיבוי ושחזור → הורד קובץ גיבוי**. הקובץ כולל
   תיקיות, פרטי מדיה, פריטים ממתינים, משתמשים ובקשות מחיקה.
2. באתר הניסוי (הפונה כברירת מחדל ל־Worker של הניסוי): **לוח הניהול → גיבוי
   ושחזור → בחר קובץ לשחזור**, ואחרי שהמסך מציג כמה תיקיות ופריטים נקראו —
   **שחזר את הנתונים**. רשומות עם אותו מזהה מתעדכנות; רשומות אחרות אינן נמחקות.

קובצי המדיה עצמם אינם מועתקים: רשומות התמונות בגיבוי מצביעות על כתובות
`/media/` של ה־Worker של הייצור, ולכן תמונות מאושרות (שהן ציבוריות) מוצגות
בניסוי ישירות מהייצור, ואילו פריטים ממתינים וקובצי צ׳אט — שדורשים התחברות —
לא ייפתחו שם. העלאות חדשות בניסוי נשמרות בדלי של הניסוי. אם במקום הגיבוי
הועתק המסד כולו (ייצוא וייבוא D1), יש להריץ בקונסולת ה־D1 של הניסוי
`UPDATE gallery_environment SET environment = 'staging' WHERE marker_key = 'environment';`
— אחרת ה־Worker של הניסוי מסרב לרוץ מול מסד שמסומן כייצור.

### העבודה היומיומית

- `main` נשאר כמו היום: PR של פיצ׳ר נפתח מול `main`, ומיזוג מפרסם לייצור.
- `staging` הוא ענף אינטגרציה, לא ענף פיתוח. לפני שינוי מסוכן דוחפים אליו
  את אותם commits — `git push origin <branch>:staging` — או פותחים את ה־PR
  מול `staging`. `checks.yml` רץ גם על דחיפות ל־`staging`, ו־`deploy-worker.yml`
  פורס לניסוי כש־`cloudflare-worker.js` השתנה; אתר הניסוי מתעדכן מ־Pages
  תוך דקה.
- מנסים ב־`https://<project>.pages.dev`, ואז ממזגים ל־`main` כרגיל.
- את `staging` מותר לאפס: `git push --force-with-lease origin main:staging`
  מחזיר אותו למצב הייצור אחרי שהניסוי הסתיים.
- פריסה ידנית: **Actions → Deploy Cloudflare Worker → Run workflow**, בחירת
  ענף ושל `target`. יעד `staging` מותר מכל ענף — כך אפשר לנסות ענף פיצ׳ר על
  ה־Worker של הניסוי בלי לגעת ב־`staging`; יעד `production` רץ מ־`main` בלבד.

### מה מגן על הייצור

- ה־Action פורס לכל Worker רק את ה־Bindings שכבר מוגדרים בו
  (`bindings_inherit=strict`) ואינו יוצר מסד או דלי. Worker ניסוי בלי
  `GALLERY_DB` או `GALLERY_BUCKET` מכשיל את הפריסה לפני ההעלאה.
- אחרי הפריסה `/health` חייב להחזיר את הסביבה המצופה; Worker ניסוי בלי
  `ENVIRONMENT=staging` נכשל כאן.
- כל מסד נושא שורת סימון (הטבלה `gallery_environment`) שה־Worker הראשון שרץ
  מולו כותב בה את שם הסביבה שלו. Worker של הניסוי שחובר בטעות למסד הייצור
  מוצא שם `production` ומסרב לשרת כל בקשה (`environment_database_mismatch`).
  ל־Binding של D1 אין שם, ולכן זו הדרך היחידה לזהות את הטעות — והיא עובדת רק
  אחרי שה־Worker של הייצור רץ פעם אחת עם הגרסה הזו וכתב את הסימון שלו; עד
  אז ההגנה היחידה היא בדיקה ידנית של ה־Bindings.
- מפתח החתימה של אסימוני ההתחברות נפרד לכל Worker, ולכן התחברות בניסוי
  אינה מקנה שום הרשאה בייצור.
- מטמון ה־Service Worker נפרד לכל מקור, ולכן אתר הניסוי אינו משפיע על
  המטמון של האתר הרגיל באותו דפדפן.

## אבטחה והרשאות

- Google ID Token נבדק בשרת וגם מול מזהה הלקוח הנכון.
- משתמש חדש נוצר תמיד בדרגת `viewer` ובמצב `pending`; הוא אינו יכול לאשר את עצמו.
- מנהל־על בלבד יכול לשנות דרגות, לחסום משתמשים ולנהל את סל המחזור.
- סודות נשמרים רק במשתני Cloudflare ואינם נכנסים ל־GitHub.
- חיפוש פנים זמין רק למשתמש מחובר ומאושר; כתיבת טביעות פנים זמינה למנהל או
  לתהליך אינדוקס מורשה בלבד.
